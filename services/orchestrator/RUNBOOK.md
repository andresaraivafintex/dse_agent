# RUNBOOK — Worker Versioning and drain-and-cutover (WSB-E1-T2)

This runbook covers how to deploy a new version of the `orchestrator`
worker without losing in-flight workflow executions and without risking
an old worker (running outdated workflow code) trying to replay
history generated by new code (or vice versa) — the classic cause of
`NonDeterministicWorkflowError` in Temporal.

## 1. Concept: a fixed `build_id` per deploy

Every worker process (`worker.py`) requires a `--build-id` (or
`DSE_WORKER_BUILD_ID`) that is **fixed and unique per deploy artifact** — normally
the short commit SHA or the container image tag:

```bash
export DSE_WORKER_BUILD_ID=$(git rev-parse --short HEAD)
python -m dse_orchestrator.worker --build-id "$DSE_WORKER_BUILD_ID"
```

**Never** reuse a `build_id` across deploys with different workflow code —
that is exactly what Temporal's versioning guarantee uses to
decide which workers may continue the history of which executions.

## 2. Two supported modes

### 2.1 Simple mode (default, Phase 1): Worker Versioning not enabled

By default (`DSE_WORKER_USE_VERSIONING=false`), the worker runs with
`build_id` used only for `identity`/observability purposes (it shows up in the
Temporal UI, making it easy to tell which deploy processed which task), **without**
enabling the server's version-compatibility enforcement. That is
appropriate for Phase 1 (small teams, infrequent deploys,
rare workflow changes) and avoids the extra operational complexity of
managing "Build ID sets" on the server.

**Deploy procedure in this mode (manual drain via `max_cached_workflows`
+ graceful shutdown):**

1. Bring up the NEW worker (new `build_id`) pointing at the SAME task queue.
   Now there are 2 workers polling the same queue.
2. Send `SIGTERM` to the OLD worker. `worker.py` handles `SIGTERM`
   by making `async with worker: await stop_event.wait()` exit the `async
   with` block, which triggers the SDK's native graceful shutdown (`Worker.shutdown`):
   it stops polling for new tasks but waits for **in-flight workflow tasks and
   activities to finish** before terminating the process.
3. Only after the old worker confirms a clean shutdown (log "worker
   stopped") should you remove it from the infrastructure (kill the container/process).
4. **Residual risk of this mode:** if the workflow code changed in a
   NON-compatible way (removed/reordered an `await` or a signal handler that already
   appears in the history of an in-flight execution), an execution that
   was "mid-flight" when the old worker went down may, once resumed by the
   new worker, fail with `NonDeterministicWorkflowError`. Mitigate by
   restricting workflow changes to purely *additive* ones
   (new signals, new branches guarded by `workflow.patched()`) during
   deploys — see section 3.

### 2.2 Worker Deployment Versioning mode (modern — plano 08 §F/F5)

> **Update (plano 08 §F, F5):** we swapped the **classic version-set**
> (`update-build-ids`, deprecated and DISABLED by default on current servers —
> `RPCError: Worker versioning v0.1 ... is disabled`) for modern **Worker Deployment
> Versioning**. The worker announces itself as version `(deployment_name,
> build_id)` with `default_versioning_behavior=PINNED` (`build_deployment_config`
> in `worker.py`). PINNED = each workflow stays STUCK to the version it started on.

Enable it with `DSE_WORKER_USE_VERSIONING=true` (or `--use-worker-versioning`).
Pin `DSE_WORKER_BUILD_ID` to the image SHA/tag and set `DSE_WORKER_DEPLOYMENT_NAME`
(default `dse-orchestrator`). Server prerequisite: deployment versioning
enabled on the namespace.

**Drain-and-cutover in this mode:**

```bash
# 1. Bring up the worker for the NEW build (e.g. build_id=git-B) pointing at the SAME
#    task queue. It registers as a new VERSION of the deployment, but it is not
#    the current one yet — no new workflow goes to it yet.

# 2. CUTOVER (a deliberate operational step — NEVER automatic at boot):
temporal worker-deployment set-current-version \
  --deployment-name dse-orchestrator \
  --build-id git-B
#    From here on, NEW workflows go to git-B. IN-FLIGHT ones stay on
#    git-A (PINNED) until they finish — that is the safe drain.

# 3. Wait for zero open executions on the old version (Temporal UI → Deployments,
#    or `temporal worker-deployment describe --deployment-name dse-orchestrator`),
#    then stop the old worker (SIGTERM, graceful drain).
```

DISABLED by default (P7 boring-first + it requires an enabled server): step 2
is an explicit CLI call, it does not happen on its own — which prevents an accidental
cutover on every restart. Enable it when the deploy cadence justifies it.

## 3. Safe vs. unsafe workflow changes

**Safe (a plain deploy works, no special drain):**
- Adding a new `@workflow.signal`/`@workflow.query`.
- Adding NEW code at the end of a phase that already ends with
  `continue_as_new` or `return` (it does not affect workflows in executions already
  closed by continue_as_new).
- Changing Activities invoked by NAME (the implementation may change freely
  on the side of the worker that executes it, without affecting the workflow history,
  which only records the *name* and the serialized *arguments/result*).

**Unsafe (requires the careful drain from section 2, or `workflow.patched()`):**
- Removing, reordering, or changing the condition of an existing `await` in the middle
  of a phase that still has open executions.
- Changing the `WorkItemLifecycleInput` payload/schema in an
  incompatible way (removing a field with a default, changing a type) without
  backward compatibility — our dataclasses have defaults on almost
  every field precisely to tolerate this better.

## 4. Post-deploy verification

```bash
curl -s http://localhost:8900/health
# {"status":"ok","build_id":"<expected>","task_queue":"dse-core-task-queue"}
```

Confirm in the Temporal UI (`http://localhost:8088`) that the `dse-core-task-queue`
task queue has active pollers and that no execution is stuck
in repeated `WorkflowTaskFailed` (a symptom of non-determinism).
